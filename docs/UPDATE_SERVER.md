# DAWASA update server

DAWASA can update itself from a folder on any HTTPS web server (for example
the existing NexusBOS VPS). The server only hosts static files; it runs no
code for DAWASA and receives no personal or financial data.

```
https://<your-domain>/downloads/dawasa/
├── index.html                  download page (website/public/index.html)
├── manifest.json               description of the latest release
├── SHA256SUMS                  checksum of the latest APK
└── dawasa-1.1.0-2.apk          signed release APKs (never overwritten)
```

`<your-domain>` is a placeholder: use a domain you control and have verified.
No production address is built into the app.

## How the app uses it

1. **Check** (automatically at most once a day when "Check for updates
   automatically" is on, or when the user taps *Check for updates*): the app
   downloads `manifest.json` with a plain `GET`. The request contains no
   identifiers, cookies or user data; the only header of note is
   `User-Agent: DAWASA/<version> (Android)`.
2. **Compare**: the manifest's `versionCode` must be higher than the
   installed one. If the installed version is below
   `minimumSupportedVersionCode` the app shows a strong "please update"
   notice, but keeps working offline.
3. **Download** (only after the user taps *Update now*; with *Wi-Fi only*
   on, mobile data needs an extra confirmation): the APK is streamed to the
   app's private cache. Interrupted downloads resume with HTTP `Range`
   requests; the user can cancel at any time.
4. **Verify**: size and SHA-256 must match the manifest. Android then reads
   the APK: package name, version code and signing certificate must match
   the installed app (and `signingCertSha256`, when given). Files that fail
   are deleted immediately.
5. **Install**: the file is handed to Android's own `PackageInstaller`
   with *user action required*. Android shows its "Do you want to update
   this app?" screen; nothing is installed silently. On first use Android
   asks the user to allow DAWASA to install updates.

Updating replaces only the APK. The user's database stays in the app's
private storage and is migrated by the new version on its first start (see
[DATABASE.md](DATABASE.md)); APK updates and database migrations are
separate steps.

### Security rules enforced by the app

* Only `https://` addresses are accepted (build configuration, the address
  typed in Settings, and the APK link).
* The APK must be on the **same host** as the manifest; redirects are only
  followed to HTTPS addresses on that host.
* Manifest size, field formats and the APK size are bounded.
* No code is ever downloaded and executed by DAWASA itself; the only thing
  downloaded is an APK that Android installs after the user confirms.

## `manifest.json`

Generated by `tool/generate_manifest.dart` — do not write it by hand.

```json
{
  "schema": 1,
  "app": "dawasa",
  "packageName": "com.sandarutharushka.dawasa",
  "minimumSupportedVersionCode": 1,
  "latest": {
    "versionName": "1.1.0",
    "versionCode": 2,
    "apkUrl": "dawasa-1.1.0-2.apk",
    "sha256": "<64 lower-case hex characters>",
    "sizeBytes": 23456789,
    "releasedAt": "2026-10-01",
    "releaseNotes": { "en": "What changed", "si": "වෙනස් වූ දේ" },
    "signingCertSha256": ["<optional: SHA-256 of the release certificate>"]
  }
}
```

`apkUrl` may be relative (recommended) or an absolute `https` URL on the
same host.

## One-time server setup (nginx)

These steps add one static folder to an existing site. They do not change,
restart or redeploy any other application on the server.

1. Create the folder and give your deploy user write access:

   ```sh
   sudo mkdir -p /var/www/dawasa/downloads/dawasa
   sudo chown -R "$USER":www-data /var/www/dawasa
   sudo chmod -R u=rwX,g=rX,o=rX /var/www/dawasa
   ```

2. Add the `location` block from
   [`website/nginx/dawasa-downloads.conf`](../website/nginx/dawasa-downloads.conf)
   inside the existing HTTPS `server { … }` block of the chosen site (or a
   new server block for a sub-domain such as `downloads.<your-domain>`).
   Back up the file first:

   ```sh
   sudo cp /etc/nginx/sites-available/<site> /etc/nginx/sites-available/<site>.bak
   sudo nano /etc/nginx/sites-available/<site>
   sudo nginx -t          # must say "syntax is ok" and "test is successful"
   sudo systemctl reload nginx
   ```

   A reload applies the change without dropping running sites. If
   `nginx -t` fails, restore the backup instead of reloading.

3. HTTPS: if the site already has a certificate nothing else is needed. For
   a new sub-domain use the existing certificate tooling (for example
   `sudo certbot --nginx -d downloads.<your-domain>`).

Other web servers work too; they must serve static files over HTTPS, support
`Range` requests, send `application/vnd.android.package-archive` for `.apk`
and should send `Cache-Control: no-cache` for `manifest.json`.

## Building the app for your server

```sh
cp config/dawasa.example.json config/dawasa.json
# edit config/dawasa.json:
#   "DAWASA_UPDATE_BASE_URL": "https://<your-domain>/downloads/dawasa/"
```

`config/dawasa.json` is ignored by Git. The address is used by
`scripts/build_release.sh` through `--dart-define-from-file`. Users can also
enter or change the address in *Settings → App updates → Update server*.

## Publishing a release

```sh
# 1. Increase the +build number in pubspec.yaml, e.g. 1.1.0+2
# 2. Build, test, sign and create the server files
scripts/build_release.sh --notes-en "What changed" --notes-si "වෙනස් වූ දේ"
# optional: pin the signing certificate
#   --signing-cert-sha256 "$(keytool -list -v -keystore <keystore> -alias <alias> | awk '/SHA256:/{print $2}')"
# 3. Upload (APK first, manifest last and atomically)
scripts/deploy_update.sh deploy@<server> /var/www/dawasa/downloads/dawasa
```

`deploy_update.sh` checks the checksum locally, uploads the APK and
`SHA256SUMS`, checks the checksum again on the server, copies the download
page, and finally replaces `manifest.json` with an atomic `mv`, so a phone
never sees a manifest pointing at a file that is not there yet. It writes
only inside the given folder.

## Checking a release

```sh
BASE=https://<your-domain>/downloads/dawasa
curl -sI "$BASE/manifest.json"            # 200, application/json, Cache-Control: no-cache
curl -sI "$BASE/dawasa-1.1.0-2.apk"       # 200, application/vnd.android.package-archive
curl -s -o /dev/null -w '%{http_code}\n' -r 0-99 "$BASE/dawasa-1.1.0-2.apk"   # 206 (resume works)
curl -s "$BASE/dawasa-1.1.0-2.apk" | sha256sum   # equals the value in manifest.json
```

Then open *Settings → App updates → Check for updates* on a phone running
the previous version.

## Rolling back

Phones only install versions with a **higher** `versionCode`. To undo a bad
release, build the previous source again with a new, higher `+build` number
and publish that. Do not delete APK files that a published manifest still
points to.

## Notes

* Keep old APK files for a while; they are small and make manual downgrades
  possible for testers.
* Web server access logs contain IP addresses and the User-Agent, like any
  website. DAWASA sends nothing else. Consider short log retention for this
  folder.
* Builds for an app store must not update themselves: build them with
  `"DAWASA_SELF_UPDATE": "false"` and remove the
  `REQUEST_INSTALL_PACKAGES` permission from the manifest for that build.
